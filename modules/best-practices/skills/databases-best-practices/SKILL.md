# Databases best practices

A curated rule set for using SQLite and PostgreSQL correctly from Python:
connection settings, transactions, concurrency, schema, and migrations.
Each rule has a stable ID and a one-line summary. Full
**What / Why / How / When-not-to-apply** entries live in `references/`,
each citing the official docs it rests on.

Wiring an async SQLAlchemy engine and sessions into a FastAPI app
(`AsyncSession` in routes, the engine in `lifespan`, Alembic instead of
`create_all()`) lives in
[`fastapi-best-practices`](../fastapi-best-practices/SKILL.md), in its
[async database rules](../fastapi-best-practices/references/async-db.md).
Language-level concerns live in
[`python-best-practices`](../python-best-practices/SKILL.md).

## When to apply this skill

Activate when any of these are true:

- A file imports `sqlite3`, opens a `.db`/`.sqlite` file, or runs `PRAGMA` statements; or the user asks about WAL, `SQLITE_BUSY`, busy timeouts, STRICT tables, or SQLite migrations.
- A file configures a PostgreSQL connection (`psycopg`, `postgresql+psycopg://`, `create_async_engine`, `pool_size`, `pool_pre_ping`), an Alembic `env.py` or migration script, or runs `SELECT ... FOR UPDATE` / advisory locks.
- The user asks whether SQLite fits a workload, how to size a connection pool, how to run migrations from several replicas, or how to avoid deadlocks.
- The user references a `SQLITE-` or `PG-` rule ID.

## How to use the rule index

1. Scan the relevant section(s) below for rule IDs that apply to the current file.
2. For each rule you intend to apply or flag, open the corresponding `references/` file and read **only that rule's entry** — they're keyed by ID.
3. Cite the rule ID when you explain a change to the user.

## Rules — SQLite

See [`references/sqlite.md`](./references/sqlite.md).

- **SQLITE-001** — Set `journal_mode=WAL` on the writer and check the mode it returns.
- **SQLITE-002** — Use `synchronous=NORMAL` with WAL: never corrupt, but the last commits can be lost on power loss.
- **SQLITE-003** — Give every connection a busy timeout (in Python, `connect(timeout=)` is it).
- **SQLITE-004** — Turn `foreign_keys` on for every connection; it's off by default.
- **SQLITE-005** — Start writes with `BEGIN IMMEDIATE`; roll back a failed `COMMIT` only if `in_transaction`.
- **SQLITE-006** — One writer connection and a pool of `mode=ro` readers, each read in one explicit transaction.
- **SQLITE-007** — Run `PRAGMA optimize = 0x10002` at open (after migrations), periodically, and at close.
- **SQLITE-008** — Key migrations on `PRAGMA user_version`, each step and its bump in one `BEGIN IMMEDIATE` transaction.
- **SQLITE-009** — Pass every value as a bound parameter.
- **SQLITE-010** — Use `STRICT` tables, `CHECK` constraints, and money as integer cents.
- **SQLITE-011** — Use `sqlite3` with `autocommit=True` (3.12+) and `check_same_thread=False`, one thread per connection at a time.
- **SQLITE-012** — Set `cache_size` (negative means KiB) and `temp_store=MEMORY` on every connection.
- **SQLITE-013** — Batch many writes into one transaction (`executemany`).
- **SQLITE-014** — Know when not to use SQLite (network filesystems, many hosts or writers); leave `mmap_size` off unless measured.
- **SQLITE-015** — Store timestamps as UTC ISO-8601 `TEXT` generated by SQLite (`strftime`).

## Rules — PostgreSQL

See [`references/postgres.md`](./references/postgres.md).

- **PG-001** — Size the per-process pool against `max_connections`; pre-ping and recycle pooled connections.
- **PG-003** — Serialize concurrent migrators with `pg_advisory_xact_lock` inside Alembic's migration transaction.
- **PG-004** — Test that the models match the migrated schema (`compare_metadata`); review autogenerated migrations.
- **PG-005** — Test each migration's upgrade → downgrade → upgrade round trip against the real Postgres image.
- **PG-013** — Lock every row a transaction will change with `SELECT … FOR UPDATE`, in one consistent order (`ORDER BY id`).
