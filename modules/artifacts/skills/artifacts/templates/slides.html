Platform briefing · Q4 2026

Pinned Marketplace Modules

Why every machine in the fleet now installs agent modules from a tagged release instead of a moving branch, and what that changed.

Dev environment team · 7 October 2026

The problem

A branch ref is not a version

  • Silent drift. Each sync pulled whatever main held that hour, so two laptops on the same commit ran different skills.
  • No rollback. Reverting meant waiting for an upstream fix; there was no older ref to point back at.
  • Three harnesses, three copies. Claude, pi and dsh each listed modules by hand and disagreed within a week.
  • Untraceable failures. A broken session never said which module revision it had loaded.

The change

One declaration, pinned refs

Before: branch refs

  • Ref main in three config files
  • Updates land on the next sync, unreviewed
  • Drift found when something breaks

After: tagged pins

  • One row per module in agents/modules.tsv
  • Ref bumps arrive as a reviewed pull request
  • --check fails CI when configs disagree

The result

11→0

fleet-wide breakages traced to upstream module drift: 11 in Q2 on branch refs, none in the twelve weeks since the pin.

How it works

From one table to three harnesses

Trade-offs

What pinning costs us

  • Slower uptake. A fix upstream reaches laptops only after the daily bump PR is reviewed and merged.
  • Review load. Roughly two bump PRs a week; most are a one-line ref change.
  • Tag discipline upstream. A module without release tags cannot be pinned and stays out of the table.

Next

Three asks for this quarter

  1. Auto-merge bump PRs whose only change is a ref, once CI is green.
  2. Record the loaded module revision in every session transcript.
  3. Move the last two hand-listed modules into the table.
